Decision flow

STEP 04실패 케이스 재분석

평균 점수보다 실제 실패 유형을 분해해 어떤 조건에서 판단이 뒤집히는지 확인했습니다.

08 / Post-project runtime audit

Running ≠ Deployable.

프로젝트 종료 후 보존 작업 중 Runtime을 Read-only로 감사하면서 발견한 별도 사례입니다. 당시 프로젝트 수행 성과와 구분합니다.

Visible state

서비스 Pod는 정상처럼 보였습니다.

애플리케이션 Pod는 Running, restart 0, age 13–15일 상태였습니다. 이미 실행 중인 Pod만 보면 즉시 장애 신호가 거의 없었습니다.

Hidden failure

신규 배포 경로는 이미 깨져 있었습니다.

온프렘 Container Registry 호스트가 응답하지 않았고, 신규 이미지 Pull이 필요한 배포는 실패했습니다. 기존 Pod는 노드 캐시 이미지로 계속 동작할 수 있었습니다.

Signal

2026-07-30에 제가 만든 주 1회 모델 드리프트 Canary의 실패가 Registry 문제를 드러낸 유일한 신호였습니다.

Root cause

Registry 연결에서 no route to host가 발생했고, 같은 LAN의 Cluster API는 정상이라 네트워크 전체 문제가 아닌 Registry Host 자체 문제로 범위를 좁혔습니다.

Gap

Canary 자체 실패에 Alert가 연결되어 있지 않아 Detection Mechanism의 실패가 다시 Silent Failure가 될 수 있었습니다.

Lesson

Workload가 Running이라는 사실과 “지금 새 버전을 안전하게 배포할 수 있다”는 사실은 다릅니다. 배포 경로와 탐지 메커니즘 자체도 관측 대상이어야 합니다.

이 Audit에서는 Read-only 원칙을 유지했고 Registry 복구나 Cluster 변경은 수행하지 않았습니다.
09 / Engineering decisions

결과보다 선택 기준을 남겼습니다.

각 문제에서 무엇을 비교했고 어떤 근거로 다음 행동을 선택했는지를 요약합니다.

Decision 01

Benchmark winner vs service-fit model

단일 품질 점수보다 Quality·Cost·Latency·Guardrail을 함께 보며 서비스 조건에 맞는 후보를 선택했습니다.

Decision 02

Extra LLM call vs deterministic fix

Guardrail 개선에서 추가 모델 호출보다 기존 근거 문자열 처리 로직을 수정하는 방식을 선택해 추가 LLM 호출 없이 개선했습니다.

Decision 03

Model issue vs upstream signal

학습 label 문제에서 모델 파라미터보다 upstream event integrity를 먼저 확인했습니다.

Decision 04

Test presence vs executable verification

테스트 코드 존재 여부가 아니라 실제 Pipeline에서 실행되는지까지 확인해야 검증 신뢰성이 생긴다고 판단했습니다.
