04 / Storage

상태 저장 워크로드와 Volume 수명주기를 실습했습니다.

단순 EmptyDir 사용이 아니라 PV/PVC Binding, Local PV와 NFS의 차이, StatefulSet과 Access Mode 제약을 확인했습니다.

Local storage

Local PV

Node와 Storage가 강하게 결합되는 구조를 실습하고 Scheduling 제약을 확인했습니다.

Shared storage

NFS

여러 워크로드에서 사용할 수 있는 공유 저장소를 구성하고 PVC와 연결했습니다.

Key pointPVC가 Pending이라고 해서 Storage 하나만 보는 것이 아니라 StorageClass, PV 조건, Access Mode, Node 제약과 Event를 함께 확인했습니다.
05 / Security

Identity, permission, configuration을 분리했습니다.

ServiceAccount와 RBAC의 관계, Secret/ConfigMap의 역할 분리, NetworkPolicy로 통신 범위를 제한하는 흐름을 실습했습니다.

Identity

ServiceAccount

Pod가 Kubernetes API와 상호작용할 때 사용하는 Identity를 구분했습니다.

Authorization

RBAC

Role / RoleBinding을 이용해 필요한 동작 범위만 허용하는 구조를 실습했습니다.

Network

NetworkPolicy

Pod 간 통신 허용 범위를 명시적으로 제한하는 정책을 적용했습니다.

06 / Scaling

Replica 수가 어떤 신호로 변하는지 확인했습니다.

HPA와 KEDA를 통해 Scaling이 단순 replica 설정이 아니라 Metric/Event와 Controller의 결정 결과임을 확인했습니다.

HPA

Resource-driven scaling

CPU/Memory 등 Resource Metric을 기준으로 replica가 조정되는 흐름을 실습했습니다.

KEDA

Event-driven scaling

외부 Event/Metric을 기준으로 워크로드가 확장·축소되는 구조를 확인했습니다.

07 / Observability

상태를 바꾸기 전에 관측 가능한 증거를 봤습니다.

Prometheus/Grafana를 이용한 Metric 관측과 Kubernetes Event/Resource State를 함께 사용해 장애 가설을 확인했습니다.

Metrics

Prometheus / Grafana

Cluster와 Workload의 리소스 사용량과 상태를 관측하고 Scaling 실습과 연결했습니다.

State

Events / Resource status

Pod, Service, PVC, RBAC 문제에서 실제 상태와 Event를 확인한 뒤 원인 범위를 좁혔습니다.

08 / Troubleshooting

증상마다 고정 명령어가 아니라 확인 순서를 만들었습니다.

아래 사례에서는 “설정을 일단 바꾼다”보다 관측 → 가설 → 확인 → 변경 → 재검증 순서로 접근했습니다.

ImagePullBackOff

Pod 상태와 Event를 확인해 Image 이름, Registry 접근, Pull 조건 중 어느 범위에서 실패했는지 좁혔습니다.

Service / Ingress

Service Selector, Endpoint, Port, Ingress Rule을 대조해 요청이 어느 계층까지 도달하는지 확인했습니다.

RBAC

ServiceAccount와 Role / RoleBinding을 비교해 어떤 API 동작에 권한이 부족한지 확인했습니다.

PVC Binding

PVC·PV·StorageClass와 Event를 확인해 Capacity, Access Mode, Node 조건 중 Binding을 막는 제약을 찾았습니다.

실습을 통해 Kubernetes 장애는 Pod 하나만 봐서는 설명되지 않는 경우가 많고, Network · Storage · Permission · Scheduling의 연결 관계를 함께 봐야 한다는 점을 확인했습니다.
